## 运行库问题

本机MinGW GCC14.2.0目标为`x86_64-w64-mingw32`。该版本官方`libsanitizer/configure.tgt`只列出受支持的目标；MinGW落入不支持分支。接受`-fsanitize`选项不代表安装中存在目标运行库。此前“只因打包漏掉libasan/libubsan”的解释撤回；不用跨操作系统/ABI的库补链接。

核对来源：GCC官方镜像的`releases/gcc-14.2.0/libsanitizer/configure.tgt`，原文保存于[源码快照](../调研/核验/20261002_gcc14.2.0_configure.tgt.txt)，SHA256为`70e8bca9504712ec0e803a75f41a73e5fcbaab2420d8ac63f95caf3deab91dad`。获取地址：`https://raw.githubusercontent.com/gcc-mirror/gcc/releases/gcc-14.2.0/libsanitizer/configure.tgt`。

Grok记录`sanitizer_oct02`没有搜索轨迹，还声称GCC14.2.0未发布、虚构MinGW配置片段。它与实际源码相矛盾，判为不可靠，保留原始返回但不作为研究结论。今后的检索摘要同样须核对原文。

已在既有Ubuntu24.04 WSL安装GCC13.3、libasan8/libubsan1等21个软件包。包来自Ubuntu官方快照，SHA256与本机APT缓存元数据一致；没有升级/删除已有软件包，没有修改Windows工具链或WSL网络设置。下载及安装脚本是`tools/wsl_gcc.ps1`，命令见[环境说明](environment.md)。

本次Linux插桩构建`dfdd5e0ce49143ff943477c1b483f3f6`通过207项核心检查、21项输出接口检查、13组CLI测试。ASan故意堆越界及UBSan故意有符号整数溢出都被检出，并以非零退出。构建、测试与完整诊断在`build/artifacts/debug-sanitized/dfdd5e0ce49143ff943477c1b483f3f6/`。它验证Linux构建，不是Windows发布程序。

## 2026-10-03 盘查补记

- 发现裸命令 `python -m unittest discover -s tests` 原先会加载 `tests/test_cli.py`，因未传 `--binary` 而产生 41 个 `WinError 2`。这是测试入口编排缺陷，不是 C 计算失败，也不应被静默忽略。
- 修正此前错误声明：SkipUnless 在解析 --binary 前执行，使流水线同样跳过所有 CLI 测试。现在改为 setUpClass 运行时检查；流水线拒绝零测试、任何跳过和不完整 OK 行，并有反例测试。旧“CLI 13组 PASS”不能证明实际执行；原历史快照保留，本补记撤回其错误结论。
- 运行管理测试在没有新鲜 Release 测试证据时会明确失败（`Test evidence missing, failed or stale`）；先运行 `python tools/pipeline.py test --configuration Release` 后恢复通过。这是证据新鲜度约束，不是计算错误。
- 当前盘查未清理 `build/` 和 `results/local/`：它们由 `.gitignore` 排除，且存在可复现证据；原始资料和历史快照未改写。大文件仍需保留，不能以目录“清洁”为由删除。
- NASA9 来源、版本、NOTICE 数据范围、文件哈希、焓基准和 134 状态软件对照已固定；这不等于独立实验验证，也不等于 HP 平衡或真实发动机性能已完成。

## TP/HP与温变冻结喷管审查

新增核心不依赖外部物理求解器；公开API均成功后提交输出。热化学模块加入纯核心边界检查，治理反例证明文件/控制台I/O不能绕过。对照工具的准备失败留下FAIL清单，runner夹具缺新增工具时不再被泛化异常断言掩盖。

独立CMake的-O3编译揭示两个回调局部状态可能未初始化的警告，修正后五项CTest通过；主流水线-O0/-O2与GCC静态分析分别留有实跑记录。固定方法结果不能补成朱雀三号或长征十号乙性能。该阶段未覆盖液态入口、气相稳定性、凝聚相/积碳、电离、沿程平衡、损失/分离、冷却与循环；旧Linux sanitizer证据不覆盖这些新增源码。后续循环范围见下节。

## 外排循环与计账审查

`prescribed_thermal_cycle_v1`已补泵/涡轮、外排支路与两路推力。审查发现旧设计只改变回流流量而没有混合其化学组成；v1现在拒绝所有非零回流字段，不能说“有压力就已实现补燃”。两项热交换分别报告所需热量，不用倒算热量证明未知燃烧正确。

Windows Release通过241项循环检查和22组CLI，CMake/Ninja 6项CTest通过。循环接入纯核心边界护栏，并用注入`printf`反例证明检查能拒绝循环I/O。归档工具重算86条方程，16种篡改JSON会失败，物理适用范围见[循环验证](cycle-validation.md)。整机没有外部同条件循环参考，也没有液态入口或煤油燃料闭合。

Pyskyfire固定7份源码/许可证由HTTP哈希核验，见[专题](../调研/专题/MOD-003_循环边界与部件参考.md)。上游使用CoolProp真实流体；这里只参考涡轮等熵/实际焓降区分和测试思路，没有整库移植。前序Grok两次502不能算资料证据。
