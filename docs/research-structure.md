# 研究怎么组织

这份规则只解决一件事：让研究问题、来源、参数、程序、结果和结论能互相追溯。使用现有任务板、参数台账和运行记录，不再另建一套重叠的“研究治理体系”。

## 一条研究路径

```text
作业要求
  → 一个可回答的问题
  → 它需要的事实和参数
  → 有明确边界的计算方法
  → C程序与独立检查
  → 结果及不确定性
  → 对问题的回答
```

研究的起点是问题，结束点也是问题的回答。检索到很多网页、搭出更多软件模块、画出更多图，并不能代替答案。

## 项目里的信息各放哪里

| 信息 | 放置位置 | 注意事项 |
|---|---|---|
| 老师要求 | `作业要求/` | 不与工程建议混写 |
| 研究问题和负责人、交付、验收 | `project/tasks.json` | 通过任务命令维护状态 |
| 一个问题的分析过程和结论 | `调研/专题/<任务ID>_主题.md` | 记录问题、证据和结论，不复制整份来源台账 |
| 可复用的来源与型号参数 | `调研/证据与参数台账.md`、后续`data/parameters/` | 一条事实只设一个正式记录位置；算例引用来源ID |
| 原始网页、论文和课件 | 现有原始资料目录 | 保存来源和版本；旧证据不静默覆盖 |
| 计算输入与输出 | `cases/`、`results/local/` | 运行目录是原始记录；可用于结论的结果需连同解释和版本说明 |
| 物理模型边界 | `docs/engineering.md`、`docs/technology-stack.md` | 明确已实现、计划中和不支持的内容 |
| 项目当前状态 | 自动生成的`worknow.md` | 不在别的文档复制一份实时状态 |
| 已经发生的工作 | `taskshot/` | 写实际操作和验证结果，不把计划写成完成 |

原始检索记录是线索，不替代台账中的原文核验。专题报告引用已有来源编号和段落/页面位置；增加新来源时先查重，再给唯一编号并保留日期。

## 专题报告最小格式

从模板开始，按实际需要删节，不必每一节都写成大段：

1. **问题**：一句话说明要查明什么，以及它会影响哪个计算或决定。
2. **回答**：目前证据支持什么；不能确定的内容直接说不确定。
3. **证据**：引用台账编号、原文定位、对象版本和日期。只列会改变判断的来源。
4. **对计算的影响**：列出可用输入、需要说明的假设、暂时未知的量。
5. **下一步或停止理由**：继续查什么；或说明为何现有资料已经够用，哪些问题超出本次范围。

如果任务只是一个文献事实核对，可以一页内完成；如果是模型分析，增加公式、条件、结果和误差。报告长度由问题决定，不由章节数量决定。

## 参数怎么进入算例

参数可以用于三种目的，必须标清：

- **验证输入**：用于验证或校准。不能再把同一数据作为独立验证结果。
- **研究输入**：来自证据或明确假设，用来回答问题。
- **敏感性输入**：按有依据的范围变化，检验结论是否改变。

每个数值说明来源、子型/批次、原始单位、工况和系统边界。事实与假设不能在同一张表里混成一列。型号字段无法证实时，就把该参数留空或列出情景；不得以同系列的某个值悄悄补上。

输入文件应引用来源ID。程序输出记录模型版本、代码构建和输入哈希；报告再说明这个结果在什么模型范围内有效。理想气体教学案例不能通过改个算例名称变成真实发动机预测。

## 什么时候一个研究问题算完成

不要求找到每一个型号未公开的参数。满足以下条件即可交付一个诚实的研究结果：

- 提出的问题得到了回答，或明确说明当前公开资料不足以回答。
- 使用的事实可追溯；假设和无法确认的字段没有隐藏。
- 计算条件及程序版本可复现，并有独立的基准、守恒关系或资料对照。
- 结论只适用于实际验证过的范围。
- 如果仍有未知项，解释它会影响哪部分结论，并给出下一条有效研究路径。
