# C算子与求解引擎：首轮调查建议

结论：先建设可诊断、可复算的小型C17引擎，逐步抽出有实验需求的算子与策略接口。**不预先承诺通用张量框架、自动计算图或整库移植。** 这里是设计建议，未改生产C模块；原工程仍按根模块登记工作。

## 建议的边界

| 层 | 职责 | 契约重点 |
|---|---|---|
| 物理/物性算子 | 固定数据上的cp/h/s、化学势、混合性质、守恒/平衡残差、导数 | 输入单位/标准态/物种身份、有效域、失败与输出有效性；依赖数据显式 |
| 数值策略 | 线性解、缩放、阻尼/线搜索、夹逼、初始化/延拓 | 接受residual/Jacobian或小体系专门接口；同一模型下可替换并公平比较 |
| 求解引擎 | 组合TP/HP、容差/预算、workspace、回退、诊断和结果接收 | 可变缓存属于实例/工作区；每次调用工作量可追踪；失败不得污染先前有效输出 |
| 研究执行层 | 单点/批量、输入快照、结果存档、性能与参考比较 | 不混入核心I/O/网络；保存输入→构建→原始结果→分析链 |

KINSOL 7.2.1 Usage §7.4.4的`KINSysFn`与`KINLsJacFn`明确用户提供方程和可选Jacobian，数值库不承担化学模型正确性。§7.4.3的`KIN_STEP_LT_STPTOL`提示小步长可为无效解附近停滞。§7.4.3的累计函数评估/迭代/回溯统计说明可靠工程需要可观测成本，不能只给最终迭代数。

## 应先补什么

1. **基线契约及诊断。** 核对每个公开API、输入域和失败不变输出；补HP整个求解的累计调用/内层迭代、回溯/冷启动和计时口径。保留现有API兼容策略，新增统计不静默改变数值结果。
2. **workspace与状态归属。** 数据只读、临时内存/热启动/学习缓存分别明确生命周期，先在现有小体系验证可重入性。提供线程/向量后端不证明同一实例可并发调用；不声称已实现线程安全。
3. **可替换策略实验。** 相同物理算子和精度下比较既有算法、简单热启动/延拓、适用的通用求解器。只抽象实际需要替换的边界，避免每个标量运算都经函数指针。
4. **导数与局部预测。** 解析导数先有独立检查；隐式灵敏度需分析Jacobian条件性，不能由“收敛”推断导数可信。近相态变化/病态处拒绝或回退。
5. **量测后再做批量后端。** 先测CPU批量、缓存命中、数据布局/向量化；有足够查询规模再比较GPU。CUDA等后端有额外编译/部署语义，不将C ABI包装说成ISO C17内核；A100训练和最终Windows生产依赖分别核查。

## 可检验的工程贡献

同精度/物理残差门槛下，域内失败更少、失败解释更完整、累计工作量或端到端成本更低，才算可证明收益。库化和目录结构本身只说明工程组织；“引擎”“算子”命名不能代替数值和适用域证据。先由WBASE量测、WREF冻结指标，再决定WEXP比较哪些策略。
